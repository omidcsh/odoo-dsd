# ADR-003: Custom route and visit models (SAP visit-list equivalent)

- **Status:** Proposed
- **Date:** 2026-11-15
- **Parent:** ADR-001

## Context

SAP DSD centers on the *visit list* / *tour*: for a given day, a driver + vehicle
execute an ordered list of customer stops. Odoo has no first-class route/visit
concept (Community has no dispatch app; `stock_picking_batch` groups pickings but
is not customer-visit oriented).

## Decision

Introduce two custom models in module `dsd_core`:

- **`dsd.route`** — a reusable route template: name, warehouse, default vehicle
  (`fleet.vehicle`), van location, driver (`res.users`), and ordered stops
  (`dsd.route.stop`: `res.partner` + sequence + day-of-week flags for frequency).
- **`dsd.route.day`** — a concrete day's run (what SAP calls the visit list):
  date, route, vehicle, driver, state (`draft → loaded → in_progress → settled`),
  generated by a wizard that snapshots the template stops for the chosen date
  (equivalent of transaction `/DSD/VC_GEN`).

Each `dsd.route.day` composes **existing** Odoo documents — no new logistics
documents are invented:

| DSD step at a stop | Odoo document |
|---|---|
| Presale order taken | `sale.order` (delivered from warehouse later) |
| Van sale / deliver | `stock.picking` (van location → customer) |
| Invoice on the spot | `account.move` from the van sale |
| Cash collected | `account.payment` (cash journal) |
| Return / empties back | `stock.picking` return (customer → van) |

A `dsd.visit` model links the route-day stop to these documents, giving one
screen per store visit (the SAP "visit execution" step) and one audit trail for
settlement.

Route *sequencing* is manual (drag stops). No route optimization/geo engine in
scope; a link-out to an external router can be added later without model changes
(lat/long fields are reserved on partners).

## Consequences

**Positive** — mirrors the proven SAP DSD shape (template → daily visit list →
execution → settlement) while every posted record is still standard Odoo stock/
sale/account data; settlement (phase 6) is pure reconciliation over these.

**Negative** — two new models to secure and test (covered by `ir.model.access.csv`
groups `group_dsd_user` / `group_dsd_manager`); manual sequencing is a known v1
limitation for large routes.
